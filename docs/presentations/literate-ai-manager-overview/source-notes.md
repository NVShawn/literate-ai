## Release Policy source refresh (2026-08-30, regeneration pending)

This source-only refresh documents the newly mandated Release Policy and project
configuration. `main` is always writable for ordinary new work in Free and Pre-release
states. Pre-release binds one `major.minor` target; `litai release rc` creates an
annotated RC only from exact green `main`. Once `release/<major>.<minor>.x` is cut, the
line is locked down. Only exact README Release Engineer logins may merge release-line
pull requests, mutate release state, create RCs, or create/publish major/minor releases.

`repository_policy.patch_authority` is `strict` or `loose`. Strict reserves patches to
Release Engineers. Loose permits a configured `writers` login to use reason-bearing
break-glass only for a trunk-first commit; it grants no RC or major/minor authority.
Every pull request carries exactly one `Literate-AI-Release: major.minor` or
`Literate-AI-Release: none` line. Peer-work terminal markers are exact-head `merged` or
reason-bearing `dead` records; dry-run-first GC rechecks open PRs, worktrees, ancestry,
protected branches, marker currency, and clean state before explicitly authorized safe
deletion.

Project-varying repository defaults are centralized under `repository_policy` in
`literate.project.json`: `default_branch`, `main_state`, `pre_release_version`,
`default_component`, `sample_component_roots`, `work_queue`, `remote`, `merge_method`,
`pull_request_labels`, `release_engineer_source`, `patch_authority`, `writers`, and
`branch_gc_minimum_age_days`. `literate.release.json` remains artifact release policy.
Authority: `src/literate_ai/contracts/projects.py`, `src/literate_ai/projects.py`,
`src/literate_ai/project_releases.py`, `src/literate_ai/application/project_tracker.py`,
and `src/literate_ai/adapters/peer_work.py`.

This is command-level enforcement. Forge branch protection should mirror it, but no live
forge configuration is claimed. The deck/narrative specifications and builders are
updated while preserving 26 slides. Local PPTX/DOCX regeneration and Google publication
were not requested and remain pending; checked-in binaries and published resources are
unchanged.

## Release evidence closure (2026-08-26)

The 0.7.0 release path now closes over its own execution evidence. The release root,
each gate, each host or worker dialog, each sample variant, and each phase records a
node in the append-only ledger implemented by `src/literate_ai/evidence_ledger.py`,
`src/literate_ai/project_releases.py`, and `src/literate_ai/step_harness.py`. Nodes
carry the pins and output pointers for their own stage; child processes inherit the
run through `LITAI_EVIDENCE_RUN` and `LITAI_EVIDENCE_PARENT`. The public
`litai release evidence explain`, `index`, `show`, and `prune` commands are the
bounded inspection and retention surface. The ledger indexes and points to evidence;
it does not authorize a build or accept a release.

Failure custody retains sample scratch, installed workspaces, transcripts, and
diagnostics on failed steps and reports their absolute paths, while successful steps
still clean up. This specifically closes the v0.5.2 host-E2E failure mode in which
the failing sample's scratch disappeared with the run that produced it. Sample
scratch remains outside the checkout; evidence custody points to that external
directory rather than relocating a host build under `_build/evidence/`.

The single-host `legacy-local` path is complete without a worker fleet. Fan-out and
provider paths that cannot run are recorded as explicit `skipped` or `unavailable`
nodes with reasons, and a fan-out without a configured fleet reports
`authoritative: false`.

## Release engineering claims used by the technical sequence

Authority: `scripts/run_checkpointed_unittests.py` and
`src/literate_ai/test_checkpointing.py` (fail-fast checkpointed resume);
`src/literate_ai/project_releases.py` and `src/literate_ai/adapters/ssh_transport.py`
(multi-target release dispatch); `src/literate_ai/perf.py` and
`src/literate_ai/cli/perf.py` (`litai perf`); `src/literate_ai/adapters/
project_lifecycle_driver.py` (`lifecycle_driver_implementation_identity`, the TCB pin)
and `docs/user/troubleshooting.md`'s "Documentation authority review is missing,
duplicate, or stale" section (the documentation-authority marker).
`docs/user/troubleshooting.md`'s "`make python-check`/`make release-check` reruns
everything after a small edit" section documents the same checkpoint mechanics for
users, not only this ledger.

- A checkpointed test/gate run records only tests or gates that actually executed and
  passed; a run interrupted partway resumes from that exact point on the next
  invocation rather than restarting. `python-check`'s checkpoint is keyed by a content
  hash of each test module's own bytes, so it is always safe to trust a resume. The
  coarser `release-check` gate-level checkpoint has no such content fingerprint — it
  tracks only the ordered gate-name list — so it is reset explicitly before
  re-validating a checkout against a different commit than it last ran against.
- A checkpointed run that resumed any prior state deliberately reports a distinct exit
  status from a genuine, from-scratch clean pass, and asks for one more full run before
  its result counts as release evidence — a resumed pass is not silently promoted to
  the same evidentiary weight as a full one.
- `litai release check --target local|github|gitlab` accepts all three target names,
  but GitLab is recognized and fail-closed as unsupported rather than dispatched.
  Local and GitHub execution use the same declared gate command
  (`make release-check`), while a single-host `legacy-local` run executes the gate
  on the invoking VM when no worker fleet is configured. Configured local fan-out
  still runs in parallel across eligible workers, requires every dispatched worker
  to pass, and names the first failing worker deterministically; absent fan-out and
  provider paths are recorded as explicit skipped or unavailable evidence. A GitHub
  Actions `--target github` pass is not a substitute claim that local fan-out ran.
- When the policy names `default_branch`, `prepare` creates `release/<major>.<minor>.x`
  if the plan says to; `check` and `publish` refuse that default branch and any
  per-patch name. Do not wrap a raw `git branch` / `git checkout` in place of `prepare`.
- SSH-dispatched remote commands run under a forced login-and-interactive shell
  (`bash -lic`) rather than sshd's default non-login, non-interactive invocation, so a
  worker's real toolchain (reached only through its own shell startup files) is
  reliably visible to the dispatched command without any worker-side configuration
  change.
- Every top-level `litai` command, and every worker dispatched during a `--target
  local` fan-out, records one structured JSON-Lines performance span: stage, target
  kind and id, coding CLI, model, start/end timestamps, duration, and pass/fail
  outcome. This telemetry is diagnostic, never authority — a read-only or missing build
  root never fails the command it observes. `litai perf show`/`litai perf chart --dir
  PATH` can report on an archived copy of that telemetry directly, so it survives past
  the disposable build directory being cleaned.
- The lifecycle driver's implementation identity is a single content-addressed digest
  over the exact declared source-file closure that is trusted to execute the project's
  build/test/acceptance lifecycle. Any change under that closure invalidates the pin;
  the project fails closed until the pin is explicitly re-recorded, which is itself a
  reviewable, single-line diff. The documentation-authority marker applies the same
  fail-closed pattern to the declared documentation surface: a stale marker blocks
  `litai project validate` until a human re-reviews and re-records it.
